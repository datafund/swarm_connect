# ADR: x402 v2 support in the gateway

- Status: proposed. It records the spike's recommendation for the epic's Phase 1 and Phase 2 work, for review in PR #635.
- Date: 2026-11-05.
- Issue: #597 (spike X0). Epic: #596.

## How to read the evidence

Every claim below carries one of three marks.

- **[ran]**: verified by running code or calling a service on 2026-11-05.
- **[read]**: verified by reading source code or documentation.
- **[inferred]**: a conclusion from the verified facts. It was not tested.

Versions used in the spike:

- Python `x402` 1.0.0 (what the gateway pins today) and 2.27.0 (latest on PyPI on 2026-11-05). Each ran in its own throwaway virtual environment, never in the repository's environment.
- `cdp-sdk` 1.51.0, the version in `requirements.lock`.
- `@x402/core` and `@x402/evm` 2.30.0 from npm. Only the source was read. Nothing from npm was run.
- httpx 0.28.1 and pydantic 2.14.3 in both throwaway environments.

## Decision summary

1. The gateway keeps its own Pydantic models for v1 and v2 and its own thin httpx facilitator client (D1, option b). It does not upgrade to `x402` 2.x in production code.
2. Python `x402` 2.x and the `@x402/core` source serve as independent checks in tests (the interop vectors for #606).
3. The `cdp-sdk` header hook stays. The new client calls it synchronously and takes the `verify`, `settle` and `supported` entries.
4. D1 to D10 are confirmed by the evidence in the table. D11 is unchanged and not tested. D1 and D5 have notes below the table. D3 has a note in its table row.

**Note on D1.** `x402` 2.x does keep a v1 path. It sends the same bytes for a canonical v1 payment [ran]. But an upgrade changes every import, the auth hook signature, error handling and the receipt bytes [ran]. Question 1 lists the differences. The addition to D1: use `x402` 2.x as a test-only oracle, not as a runtime dependency.

**Note on D5.** The v2 `exact` payload carries the same EIP-3009 `authorization` object as v1: `from`, `to`, `value`, `validAfter`, `validBefore` and `nonce` [ran, live capture]. The EIP-712 signature covers the authorization and the token domain. It does not cover the x402 version [read, `x402/mechanisms/evm/exact`]. So one signature can be wrapped in a v1 or a v2 envelope [inferred]. A version-specific replay key would let it through twice [inferred].

## Recommended facilitator approach

Use one gateway-owned async client, about 150 lines, built on httpx.

- It sends `POST {url}/verify` and `POST {url}/settle` with `{"x402Version", "paymentPayload", "paymentRequirements"}`. The body shape is the same for both versions [read, both libraries; ran, live and stub captures].
- It sends `GET {url}/supported` at startup when v2 is enabled (D3).
- It serializes with `by_alias=True, exclude_none=True` and compact JSON. That gives the same bytes as `x402` 1.0.0 for a canonical v1 payment [ran].
- It sets an explicit timeout. `x402` 1.0.0 uses the httpx default of 5 seconds [read, ran]. `x402` 2.x uses 90 seconds [read].
- It keeps today's rule for outcomes. A parsed `success: false` is a definite refusal. A transport error, a timeout or an unreadable answer is an unknown outcome (`app/x402/settlement.py`) [read]. The client decides how to classify a non-200 answer explicitly, instead of inheriting a library's choice.
- Auth: it calls `create_headers()` before each request and merges the entry for the path (`verify`, `settle`, `supported`). The CDP hook and the bearer-token hook both fit this [ran, Question 2].
- Facilitators: x402.org for Base Sepolia. For Base mainnet, CDP or PayAI. Both PayAI and x402.org accept v1 and v2 `exact` today (Question 3).

## Question 1: library or own models (D1)

### Does `x402` 2.x still contain v1 models and a v1 code path?

Yes.

- `x402.schemas.v1` has `PaymentPayloadV1`, `PaymentRequirementsV1`, `PaymentRequiredV1` and `SupportedResponseV1` [ran, imported].
- `x402.mechanisms.evm.exact.v1` has a v1 client and a v1 facilitator [read].
- `x402.http.HTTPFacilitatorClient.verify` and `.settle` accept `PaymentPayload | PaymentPayloadV1`. They take `x402Version` from the payload [read, `http/facilitator_client.py`].
- `register_exact_evm_client` registers both v2 (`eip155:*`) and the v1 network names [read].

### Does it pass a v1 payload through unchanged?

Yes for a canonical v1 payment. Not for every input.

Method [ran]: a local stub HTTP server recorded the request bodies. The same v1 payload and the same requirements (as `create_payment_requirements` builds them) went through `x402` 1.0.0 `FacilitatorClient` and `x402` 2.27.0 `HTTPFacilitatorClient`.

- The `/verify` bodies were byte-identical: 909 bytes each.
- The `/settle` bodies were byte-identical: 909 bytes each.
- `Content-Type` and the `Authorization` header from `create_headers` were the same.

Differences found [ran]:

1. Unknown fields. 1.0.0 parses `payload` into a typed `ExactPaymentPayload` and drops fields it does not know. 2.x keeps `payload` as a plain dict and forwards unknown fields to the facilitator.
2. Network names. 1.0.0 accepts four v1 names only (`base`, `base-sepolia`, `avalanche`, `avalanche-fuji`). 2.x accepts any string in a v1 payload.
3. Non-200 answers. 1.0.0 parses the body whatever the status. A body without `success` raises a pydantic `ValidationError`. 2.x raises `ValueError("Facilitator settle failed (500): ...")` for any non-200 status.
4. Refusals without `transaction`. 2.x `SettleResponse` requires `transaction` and `network`. A body of `{"success": false, "errorReason": "..."}` fails `SettleResponse.model_validate`. `_parse_facilitator_response` (in `x402/http/facilitator_client.py`) catches that `ValidationError` and raises `FacilitatorResponseError`. In 1.0.0 it returns `success=False`. x402.org and PayAI both send `"transaction": ""` with a refusal, so they parse in both versions [ran, invalid-signature probe].
5. Receipt bytes. `SettleResponse.model_dump(by_alias=True)` in 2.x adds `errorMessage`, `amount`, `extensions` and `extra`, and reorders keys. The gateway puts that dump in `X-PAYMENT-RESPONSE` (`encode_payment_response`), so the header would change.
6. Auth hook. 2.x calls `create_headers()` synchronously. The gateway's current async wrapper in `app/x402/facilitator.py` fails with `AttributeError: 'coroutine' object has no attribute 'get'`.

Differences 3 and 4 matter most [inferred]. `app/x402/settlement.py` treats an exception as an unknown outcome (502 `PAYMENT_SETTLEMENT_UNKNOWN`) and `success: false` as a definite refusal. With 2.x, some refusals would turn into unknown outcomes.

### What an upgrade to 2.x would change

- `x402.types` and `x402.encoding` no longer exist [ran]. Models move to `x402.schemas` and `x402.schemas.v1`. The base64 helpers move to `x402.http`.
- `x402.facilitator` still exists but holds the facilitator-side engine. It has no `FacilitatorClient` or `FacilitatorConfig` [ran]. The client is `x402.http.HTTPFacilitatorClient`. `x402.http.FacilitatorClient` is a `Protocol`.
- `FacilitatorConfig` becomes a dataclass with an `auth_provider`. A dict with `create_headers` still works, but the callable must be synchronous [read, ran].
- `x402PaymentRequiredResponse` becomes `PaymentRequiredV1`.
- Error semantics and receipt bytes change, as listed above.
- `requirements.txt` says the pin exists because "v2.x has breaking API changes". The spike confirms that.

### Recommendation: (b) own models plus a thin httpx client, with 2.x as a test oracle

Trade-offs:

| | (a) Upgrade to `x402` 2.x | (b) Own models and client | (c) Hybrid: 2.x models, own client |
|---|---|---|---|
| Code to write | Least | About 150 lines of client and about 150 lines of models | Client only |
| Change to existing code | All 3 app files and 17 test files, plus error handling | The same 3 app files, the same 17 test files | Both kinds of change |
| v1 behaviour stays byte-identical | Request bodies yes. Receipts and error handling no | Yes, by construction and by test | Request bodies yes. Model dumps no |
| Control of refusal versus unknown outcome | Library decides | Gateway decides | Gateway decides |
| Upstream churn | Follows a fast-moving 2.x line (2.26 to 2.27 within weeks) | None at runtime | Models still follow upstream |
| Runtime dependencies | Adds `nest-asyncio`; extras pull `web3>=7.15` | Removes `x402`. `web3` and `eth-*` stay as direct requirements | Keeps `x402` |
| Risk of spec drift | Low | Needs interop tests (#606) | Low for models |

Option (b) is better on the two things this gateway cares about most: v1 stays byte-identical in Phase 1, and the settlement code keeps control of what counts as "not charged" [inferred]. The cost is owning the v2 shapes. The interop tests in #606 cover that, using `x402` 2.x and the `@x402/core` vectors below as independent references.

## Question 2: CDP auth with the recommended client

Yes, for both versions.

- `cdp.x402.create_facilitator_config` returns `{"url": "https://api.cdp.coinbase.com/platform/v2/x402", "create_headers": <sync function>}` [read, ran with a throwaway Ed25519 key and no network call].
- `create_headers()` returns a dict keyed by path: `verify`, `settle`, `supported`, `list` [ran].
- Each entry has `Authorization: Bearer <JWT>`, `Content-Type` and `Correlation-Context` [ran].
- The JWT claim `uris` is `["POST api.cdp.coinbase.com/platform/v2/x402/verify"]` (or `/settle`). It expires after 120 seconds [ran, decoded].
- The JWT does not cover the request body. `request_body` is only used for wallet auth, which the x402 paths do not need [read, `cdp/auth/utils/http.py`].
- So the headers do not depend on `x402Version` [inferred from the two facts above].
- The JWT is short-lived, so the client must call `create_headers()` for each request, as both `x402` libraries do [read].
- Not tested: whether CDP settles v1 payments (#524). No CDP credentials were available, and CDP was not called.

## Question 5: header size

Method [ran]: the gateway's own `create_payment_requirements` and description strings built each offer for a placeholder hostname of 29 characters. That is about the length of a typical deployed gateway hostname. The hostname appears once in `PAYMENT-REQUIRED`, so each extra character adds about 1.33 base64 characters [inferred]. The script mapped the v1 offer to the v2 shape below, serialized it with compact JSON (the same spacing as `JSON.stringify`), and base64-encoded it. Inputs were chosen near the largest values: an upload with every query parameter and redundancy 4 at the 10 MB limit, and a stamp purchase with a 12-digit `amount`.

| Route | Network | v2 JSON | `PAYMENT-REQUIRED` (base64) |
|---|---|---|---|
| `POST /api/v1/stamps/` | `eip155:8453` | 470 B | 628 chars |
| `POST /api/v1/pool/acquire` | `eip155:8453` | 484 B | 648 chars |
| `POST /api/v1/data/` (all query parameters) | `eip155:8453` | 715 B | **956 chars** |
| `POST /api/v1/data/` (all query parameters) | `eip155:84532` | 712 B | 952 chars |

- Every 402 has one offer in `accepts` today [read, every `accepts` in `app/`].
- With more offers (for example, more networks), each adds about 310 characters: about 1.9 KB for 4 offers and 3.1 KB for 8 [ran, estimate from the offer size].
- The v2 request header `PAYMENT-SIGNATURE` for the largest upload is about 1,472 characters, because it repeats `accepted` and `resource` [ran, built with full-length fields].
- `PAYMENT-RESPONSE` is about 236 characters [ran].

Limits:

| Limit | Value | Applies to | Largest header | Fits |
|---|---|---|---|---|
| Caddy `reverse_proxy` `max_response_header` | 10 MiB [read, caddyserver.com docs] | `PAYMENT-REQUIRED`, `PAYMENT-RESPONSE` | 956 chars | yes |
| Caddy `max_header_size` (client request headers) | 16 KiB [read, caddyserver.com docs] | `PAYMENT-SIGNATURE` | about 1.5 KB | yes |
| nginx `large_client_header_buffers` default | `4 8k`: one request header field at most 8 KB [read, nginx.org docs] | `PAYMENT-SIGNATURE` | about 1.5 KB | yes |
| nginx `proxy_buffer_size` default | 4 KB or 8 KB: the whole upstream response header block in one memory page [read, nginx.org docs] | all 402 response headers together | 956 chars plus the other headers | yes, but this is the tightest limit [inferred] |
| Cloudflare | Often quoted as 16 KB per header and 32 KB total. Cloudflare's current docs state 128 KB total for request headers and 128 KB for response headers [read, developers.cloudflare.com] | both | 956 chars | yes, under either figure |
| MCP `MAX_PAYMENT_HEADER_CHARS` | 8192 chars [read, `swarm_provenance_mcp/gateway_client.py`, datafund/swarm_provenance_MCP#276] | `PAYMENT-REQUIRED` | 956 chars | yes |

The repo's reverse proxy is Caddy (`deploy/Caddyfile`, `docs/deployment-guide.md`, `docs/mainnet-runbook.md`) [read]. The repo does not describe Cloudflare or nginx in front of the gateway [read]. No change is needed. Keep `resource.url` free of large query values. It is the only part that grows with the request [inferred].

## Question 6: v2 message shapes (interop vectors for #606)

Source: `@x402/core` 2.30.0, `dist/esm/x402Client-*.d.mts` (types) and `dist/esm/chunk-*.mjs` (zod schemas `PaymentRequiredV2Schema`, `PaymentPayloadV2Schema`, `PaymentRequirementsV2Schema`, `ResourceInfoSchema`) [read]. The payload and settle examples were checked against the live exchange in Question 4 [ran]. Python `x402` 2.27.0 `x402/schemas/payments.py` and `responses.py` agree [read].

Placeholders: `<pay-to>` and `<payer>` are 0x-prefixed 20-byte addresses. `<nonce>` is 32 random bytes in hex. `<signature>` is the 65-byte EIP-712 signature in hex. `<valid-before>` is a Unix time in seconds, as a decimal string. The asset is Base mainnet USDC.

Field rules from the schemas:

- `PaymentRequired`: `x402Version` is the literal `2`. `resource` is required, with a non-empty `url`. `accepts` has at least 1 and at most 1024 entries (`maxPaymentAccepts`). `error` and `extensions` are optional.
- `ResourceInfo`: `url` is required. `description`, `mimeType`, `serviceName`, `tags` and `iconUrl` are optional. `serviceName` is at most 32 printable ASCII characters. `tags` has at most 5 entries, each at most 32 printable ASCII characters. `iconUrl` is at most 2048 characters.
- `PaymentRequirements` (v2): `scheme`, `network`, `amount`, `asset` and `payTo` are non-empty strings. `network` must match the CAIP-2 regex `/^[-a-z0-9]{3,8}:[-_a-zA-Z0-9]{1,32}$/` (`NetworkSchemaV2` in `@x402/core` 2.30.0, `_validate_caip2_network` in Python `x402` 2.27.0). `maxTimeoutSeconds` is a positive number. `extra` is an optional object: it may be absent or `null` (`OptionalAny`).
- `PaymentPayload` (v2): `x402Version` is `2`. `accepted` is one entry from `accepts`, copied. `payload` is scheme-specific. `resource` and `extensions` are optional.
- `SettleResponse`: `success`, `transaction` and `network` are required. `transaction` is `""` on a refusal. `errorReason`, `errorMessage`, `payer`, `amount`, `extensions`, `extensionResponses` and `extra` are optional.
- Headers are base64 of the UTF-8 JSON (`safeBase64Encode(JSON.stringify(...))`).

### `SettleResponse` (facilitator answer, and base64-encoded in `PAYMENT-RESPONSE`)

Success, as returned in Question 4:

```json
{
  "success": true,
  "transaction": "<transaction hash>",
  "network": "eip155:84532",
  "payer": "<payer>"
}
```

Refusal:

```json
{
  "success": false,
  "errorReason": "invalid_exact_evm_non_canonical_signature",
  "transaction": "",
  "network": "eip155:84532",
  "payer": "<payer>"
}
```

The refusal shape is the v1 answer from the invalid-signature probe in Question 3, with the v2 network name [ran for v1; inferred for v2].

### `VerifyResponse` (facilitator answer to `/verify`)

```json
{
  "isValid": true,
  "payer": "<payer>"
}
```

`isValid` is required. `invalidReason`, `invalidMessage`, `payer`, `extensions`, `extensionResponses` and `extra` are optional [read, `@x402/core` 2.30.0 types]. A failure has `"isValid": false` and `invalidReason`.

## Open questions

1. Does CDP settle v1 payments (#524)? This needs CDP credentials. If it does not, v2 is the only way to Base mainnet through CDP.
2. Which v2 kinds does CDP's `/supported` list for `eip155:8453`? It needs an authenticated call.
3. How should the gateway's client classify a non-200 facilitator answer that has a parseable `success: false` body? The current 1.0.0 client accepts it as a refusal. Decide this in #606 and test it.
4. Should the v2 client forward unknown fields in `payload` (as `x402` 2.x does) or drop them (as 1.0.0 does)? Dropping keeps v1 byte-identical. Forwarding is safer for future scheme fields.
5. The epic's open questions on sunset criteria, client v1 support after removal, and the dashboard are unchanged by this spike.
